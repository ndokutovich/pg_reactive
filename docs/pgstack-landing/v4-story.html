In 2021, pgvector added vector search to PostgreSQL

Overnight, every database needed an embedding column. A single C extension changed what people expected from Postgres.

The same thing is about to happen to realtime.

The polling tax

Every production codebase has the same dirty secret. Somewhere in the stack, a setInterval fires every five seconds. A cron job wakes up to re-run a query. A websocket handler polls the database, diffs the result in application code, and pushes the difference to the client. The pattern is so universal that nobody questions it anymore.

The cost is invisible until it isn't. A dashboard with 200 concurrent users means 200 identical queries hitting Postgres every few seconds. A leaderboard with a million rows gets re-sorted on every poll. An analytics panel runs the same GROUP BY over and over, hoping to catch the moment something changes. Most of the time, nothing has.

We accepted this because we had no alternative. PostgreSQL could store the data. It could query the data. But it could not watch the data.

What if SELECT could notify you when its result changes?

How pg_reactive works

pg_reactive is a PostgreSQL C extension. You install it with CREATE EXTENSION. No sidecar, no extra process, no external service. It runs inside the database engine itself.

You give it any SELECT query—joins, aggregates, window functions, CTEs, subqueries. pg_reactive registers the query as a live subscription. Under the hood, it tracks which columns in which tables the query reads from, and installs lightweight triggers on those columns. When a row changes, the triggers fire. pg_reactive re-evaluates only the affected portion of the query, computes an EXCEPT-based diff against the previous result set, and emits the delta as a JSON payload over PostgreSQL's native LISTEN/NOTIFY channel.

The diff is precise. If a single row enters the result set, you get that row. If an aggregate changes because one underlying value shifted, you get the new aggregate value and the old one. The client never re-fetches the full result. It applies the delta to its local copy and moves on.

SELECT reactive.subscribe(
  'channel_leaderboard',
  $$
    SELECT user_id, username, SUM(score) AS total
    FROM game_scores
    JOIN users USING (user_id)
    GROUP BY user_id, username
    ORDER BY total DESC
    LIMIT 100
  $$
);

That's it. Any client listening on channel_leaderboard now receives JSON deltas whenever any score changes. The GROUP BY re-aggregates. The ORDER BY re-sorts. The LIMIT re-applies. And only the difference arrives.

pg_ivm gave us incremental view maintenance—refresh a materialized view without recomputing from scratch. pg_reactive gives us push.

With pg_ivm, you still have to ask. You call REFRESH, and it updates the view efficiently. But you decide when to ask. You're still polling, just with a smarter refresh.

pg_reactive inverts the model. You don't ask. The database tells you. The moment a relevant row changes, the delta arrives. No refresh call, no timer, no coordination. The query watches itself.

The Materialize question

Materialize does this. It does it well. You write SQL, you get incremental results. But Materialize is a separate database. It requires its own cluster, its own operational burden, its own billing line. The starting price is $820 per month. For a startup with a single Postgres instance, that's not a tool—it's a commitment.

pg_reactive is not a replacement for Materialize at scale. If you need thousands of concurrent materializations across terabytes, Materialize earns its price. But for the vast majority of applications—dashboards, leaderboards, notification feeds, collaborative documents, admin panels— you don't need a second database. You need your existing one to be a little smarter.

What becomes possible

A collaborative spreadsheet where cell formulas update across clients the instant the underlying data changes. A stock trading dashboard where portfolio aggregates recompute without a single poll. A SaaS admin panel where every metric is live by default, not because you built a websocket layer, but because the database pushes diffs natively.

A multi-tenant analytics page where each customer sees their own live GROUP BY. A monitoring system where alert thresholds are just SQL predicates on a subscribed query. A notification service that doesn't wake up on a timer—it wakes up when the data says so.

None of this requires Kafka. None of it requires a streaming platform. None of it requires anything beyond the PostgreSQL you already operate.

Under the hood

pg_reactive is written in C against the PostgreSQL extension API. It hooks into the query planner to extract column-level dependencies, then installs per-column triggers that fire only when watched values change. The diff engine uses PostgreSQL's own EXCEPT operator internally, applied to the minimal subset of the result set that could have been affected.

Deltas are serialized as JSON with three arrays: added rows, removed rows, and changed rows (with both old and new values). The payload is delivered via LISTEN/NOTIFY, which means any PostgreSQL client library that supports notifications can receive live updates with zero additional infrastructure.

-- Delta payload structure
{
  "added": [{ "user_id": 42, "total": 1580 }],
  "removed": [{ "user_id": 17, "total": 990 }],
  "changed": [{ "user_id": 8, "old": { "total": 1200 }, "new": { "total": 1340 }}]
}

Subscriptions are transactional. If the INSERT that triggered a change rolls back, no delta is emitted. What the client sees is always consistent with committed database state.
