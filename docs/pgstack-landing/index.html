Subscribe to any SELECT in PostgreSQL

GROUP BY, window functions, JOINs, aggregates. Get JSON deltas when results change. No Kafka, no Materialize, no extra process.

Get Started Compare Solutions
subscribe.sql 
-- Subscribe to a live aggregate
SELECT pgr.subscribe(
  'orders_by_status',
  'SELECT status, COUNT(*) as cnt
   FROM orders
   GROUP BY status'
);

-- When data changes, you receive:
-- { "changed": [{ "status": "pending", "cnt": 43 }] }

-- Not row events. The actual query result.

The Problem

Every dashboard polls. Yours doesn't have to.

The entire industry accepted polling as the norm. Materialize costs $820/mo. pg_ivm can't push. Supabase Realtime is row-level only.

Before: Polling

dashboard.ts
setInterval(async () => {
  const { data } = await db.query(
    `SELECT COUNT(*)
     FROM orders
     WHERE status = 'pending'`
  )
  updateDashboard(data)
}, 5000) // every 5 seconds...

Wastes DB resources. 5-second lag. Scales linearly with users.

After: pg_reactive

dashboard.ts
client.subscribe(
  `SELECT COUNT(*)
   FROM orders
   WHERE status = 'pending'`,
  (delta) => updateDashboard(delta)
)

// ~3ms from commit to screen
// Zero polling. Push model.

Notifies on change. Millisecond latency. Constant DB load regardless of users.

Architecture

How pg_reactive works

A C extension inside PostgreSQL. Not a sidecar, not a proxy, not a separate database. Works within the transaction commit path.

Column-level tracking

Analyzes your query AST. Only recomputes when columns your query references actually change. UPDATE on an unrelated column? Nothing happens.

EXCEPT-based diff

Compares current result with previous snapshot using SQL EXCEPT. Gives exact delta: what was added, removed, changed. Not a full refresh.

Shared memory snapshots

1024+ concurrent subscriptions with LRU eviction. Snapshots live in PostgreSQL shared memory. Configurable via GUC parameters.
