PostgreSQL Extension

Subscribe to any SELECT query

pg_reactive is a PostgreSQL C extension that lets you subscribe to any SELECT query and receive JSON deltas whenever the results change. GROUP BY, window functions, aggregates, JOINs -- all work out of the box. No extra process, no Kafka, no Materialize. Just PostgreSQL.

SQL 
SELECT pgr.subscribe(
  'channel_stats',          -- subscription name
  $$
    SELECT channel, COUNT(*) as msgs, MAX(created_at) as latest
    FROM messages
    GROUP BY channel
  $$
);

When any INSERT, UPDATE, or DELETE changes the query's results, connected clients receive a JSON delta on the channel_stats NOTIFY channel:

JSON delta 
{
  "added":   [{ "channel": "#releases", "msgs": 1, "latest": "..." }],
  "removed": [],
  "changed": [{ "channel": "#general", "msgs": 342, "latest": "..." }]
}
PostgreSQL Licensed

pg_reactive is open source. pgStack is the production wrapper that adds auth, REST, live queries over WebSocket, and TLS -- all in one container.

Subscribe API

The core function. Takes a name and a query, returns a subscription handle. When underlying data changes, the extension re-evaluates the query and emits a JSON delta via NOTIFY.

SQL 
pgr.subscribe(
  name     text,              -- NOTIFY channel name
  query    text,              -- any SELECT query
  params   jsonb DEFAULT '{}' -- bind parameters
) RETURNS subscription_id

Parameters

ParameterTypeDescription
name text The NOTIFY channel name. Clients LISTEN on this channel to receive deltas.
query text Any valid SELECT -- including GROUP BY, window functions, CTEs, subqueries, JOINs.
params jsonb Optional. Named bind parameters as JSON object. Referenced in query as $name.

Lifecycle

FunctionReturnsDescription
pgr.subscribe() subscription_id Creates subscription. Installs triggers on referenced tables. Snapshots initial result.
pgr.unsubscribe(name) void Removes subscription and associated triggers. Frees shared memory slot.
pgr.list() setof record Lists all active subscriptions with name, query, table dependencies, and last-fire timestamp.
pgr.version() text Returns the installed pg_reactive version string.

Delta format

Every notification payload is a JSON object with three arrays:

TypeScript 
interface PgrDelta<T> {
  added:   T[];   // rows in new result but not in previous
  removed: T[];   // rows in previous result but not in new
  changed: T[];   // rows present in both but with different values
}

Examples

GROUP BY aggregation

Subscribe to a live leaderboard. Every time a score is inserted, the top-10 re-ranks automatically.

SQL 
SELECT pgr.subscribe(
  'leaderboard',
  $$
    SELECT
      u.name,
      SUM(s.points) AS total,
      COUNT(*)       AS games
    FROM scores s
    JOIN users u ON u.id = s.user_id
    GROUP BY u.name
    ORDER BY total DESC
    LIMIT 10
  $$
);
TypeScript 
import { Client } from 'pg';

const client = new Client('postgres://127.0.0.1/app');
await client.connect();
await client.query('LISTEN leaderboard');

client.on('notification', (msg) => {
  const delta = JSON.parse(msg.payload);
  // delta.added   -- new entries in top 10
  // delta.removed -- dropped out of top 10
  // delta.changed -- score/rank updated
  updateUI(delta);
});

Window functions

Track running totals and rank changes in real time. The subscription fires when any row's computed window value changes.

SQL 
SELECT pgr.subscribe(
  'sales_running',
  $$
    SELECT
      rep_name,
      amount,
      SUM(amount) OVER (
        PARTITION BY rep_name
        ORDER BY closed_at
      ) AS running_total,
      RANK() OVER (
        ORDER BY SUM(amount) OVER (PARTITION BY rep_name) DESC
      ) AS team_rank
    FROM deals
    WHERE closed_at >= CURRENT_DATE - INTERVAL '30 days'
  $$
);
TypeScript 
// Using pgStack WebSocket (auto-reconnect built in)
const ws = new WebSocket('ws://127.0.0.1:3000/live');

ws.send(JSON.stringify({
  action: 'subscribe',
  channel: 'sales_running',
  token: jwtToken
}));

ws.onmessage = (e) => {
  const { channel, delta } = JSON.parse(e.data);
  if (channel === 'sales_running') {
    renderDashboard(delta);
  }
};

Parameterized queries

Bind user-specific parameters so each client only receives deltas relevant to them.

SQL 
SELECT pgr.subscribe(
  'user_notifications_42',
  $$
    SELECT id, title, read, created_at
    FROM notifications
    WHERE user_id = $user_id
      AND created_at > NOW() - INTERVAL '7 days'
    ORDER BY created_at DESC
  $$,
  '{"user_id": 42}'::jsonb
);
TypeScript 
// pgStack handles per-user subscription routing
ws.send(JSON.stringify({
  action: 'subscribe',
  channel: 'user_notifications',
  params: { user_id: currentUser.id },
  token: jwtToken
}));

// Delta arrives only when THIS user's notifications change
ws.onmessage = (e) => {
  const { delta } = JSON.parse(e.data);
  mergeNotifications(delta);
};

Architecture

pg_reactive runs entirely inside PostgreSQL. No sidecar, no CDC pipeline, no external process. Here is how it detects changes to arbitrary queries.

EXCEPT-based diffing

When a subscription fires, pg_reactive re-executes the subscribed query and computes a diff against the previous snapshot using SQL EXCEPT. This is the same mechanism PostgreSQL uses internally for EXCEPT set operations -- hash-based, well-optimized, and already battle-tested.

Internal diff (conceptual)
-- Rows added (in new, not in old)
(SELECT * FROM new_result) EXCEPT (SELECT * FROM prev_snapshot);

-- Rows removed (in old, not in new)
(SELECT * FROM prev_snapshot) EXCEPT (SELECT * FROM new_result);

Column tracking and trigger installation

At subscription time, pg_reactive parses the query to identify referenced tables and columns. It installs AFTER triggers only on the columns that matter. If your query reads messages.channel and messages.created_at, an update to messages.body will not fire the subscription.

The trigger function is lightweight: it sets a flag in shared memory indicating the subscription needs re-evaluation. The actual re-query happens asynchronously in a background worker, outside the triggering transaction.

Shared memory and batching

pg_reactive allocates a fixed shared memory segment at server start (configurable via pg_reactive.shmem_size). Each subscription occupies one slot containing:

  • The subscription metadata (name, query text, params)
  • A serialized snapshot of the last result set
  • A dirty flag set by triggers, cleared after re-evaluation

Multiple writes in a single transaction produce only one re-evaluation. The background worker coalesces dirty flags and processes all pending subscriptions in a single pass, typically within 10-50ms of COMMIT.

No WAL dependency

Unlike CDC-based tools, pg_reactive does not read the WAL. It uses standard SQL queries and triggers. This means it works with any PostgreSQL-compatible system that supports C extensions -- including self-hosted, bare-metal, and some managed providers that allow custom extensions.

Trade-off

pg_reactive re-executes the full query on each change. Materialize maintains incremental dataflows. For high-throughput streams (10k+ writes/sec), Materialize will be faster. For typical application workloads (up to ~1k writes/sec on subscribed tables), pg_reactive adds negligible overhead and eliminates an entire infrastructure layer.

Limitations

pg_reactive is in beta. Here is what you should know before deploying.

  • Managed PostgreSQL. AWS RDS, Azure Flexible Server, and Google Cloud SQL do not allow custom C extensions. You need self-hosted PostgreSQL, or a provider that supports custom extensions (Crunchy Bridge, Supabase self-hosted, Neon with custom builds).
  • Subscription count. Tested with up to ~200 concurrent subscriptions. Performance above 500 is untested and may degrade as the background worker iterates all dirty flags sequentially.
  • Large result sets. Each subscription snapshot is held in shared memory. Queries returning thousands of rows per subscription will consume significant shmem. Keep subscribed result sets small (use LIMIT, filter aggressively).
  • DDL changes. Altering a subscribed table's schema (adding/dropping columns) will invalidate affected subscriptions. You must pgr.unsubscribe() and re-subscribe after DDL.
  • Replication slots. pg_reactive does not use logical replication, so it does not conflict with existing replication setups. However, the background worker does hold a lightweight connection that counts toward max_connections.
  • PostgreSQL 15+ required. The extension uses APIs introduced in PostgreSQL 15. It will not compile against earlier versions.

PostgREST compatibility

pgStack's REST API is wire-compatible with PostgREST. If you already use PostgREST, your existing client code works unchanged. The /live WebSocket endpoint is the addition -- it multiplexes pg_reactive subscriptions over a single connection per client.

Shell 
# Standard PostgREST queries work
curl http://127.0.0.1:3000/rest/users?select=id,name&role=eq.admin

# Live queries over WebSocket
wscat -c ws://127.0.0.1:3000/live \
  -x '{"action":"subscribe","channel":"leaderboard","token":"eyJ..."}'
