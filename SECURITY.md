# Security Policy

## Supported Versions

This project is on pre-1.0. Security fixes land on `master` and are released in
the next tagged version. We do not yet maintain backports — please upgrade to
the latest release.

| Component        | Versioning                                        |
|------------------|---------------------------------------------------|
| C extension      | Tracked in `ext/pg_reactive.control` (`default_version`) |
| Go proxy         | Tracked by git tag on the monorepo                |
| TypeScript SDK   | `sdk/package.json` (semver, published separately) |
| CLI              | `cli/package.json` (semver, published separately) |

## Reporting a Vulnerability

**Do not** open a public GitHub issue for security reports.

Email: **ndokutovich@gmail.com** with subject prefix `[pg_reactive security]`.

If you prefer encrypted communication, include a PGP key request in your
initial message and we will respond with a key fingerprint.

Please include:

- Affected component (`ext/`, `proxy-go/`, `sdk/`, `studio/`, `cli/`)
- Affected version or commit SHA
- A minimal reproduction (proof-of-concept code, request, or steps)
- Your assessment of impact (data exposure, RCE, auth bypass, DoS, etc.)
- Whether the issue is being actively exploited

### What to expect

- **Acknowledgement** within 72 hours.
- **Initial triage** within 7 days — confirming the issue, severity rating, and
  expected timeline.
- **Fix and disclosure** coordinated with the reporter. We aim for ≤ 30 days for
  high-severity issues and ≤ 90 days for medium/low. Critical issues may
  ship out-of-band.

We will credit reporters in release notes unless you ask to remain anonymous.

## Scope

In scope:

- The C extension (`ext/`) — SQL injection, RLS bypass, shared-memory safety,
  privilege escalation through `pgr.subscribe()` / `pgr.unsubscribe()`.
- The Go proxy (`proxy-go/`) — auth flows (JWT, OAuth, refresh tokens),
  PostgREST-compatible REST, RLS context handling, WebSocket auth and
  audience enforcement, edge function sandboxing, webhook delivery (SSRF),
  rate limiting, CORS / CSP / HSTS.
- The TypeScript SDK (`sdk/`) — token storage (sessionStorage discipline),
  XSS surface, realtime channel validation.
- The Studio UI (`studio/`) — XSS, CSRF, privilege checks.
- Infrastructure (`docker-compose.prod.yml`, deploy workflows) — secret
  handling, exposed ports, supply chain.

Out of scope:

- Issues that require physical access to the host or PostgreSQL superuser
  credentials.
- Self-XSS that requires the victim to paste malicious code into a console.
- Vulnerabilities in dependencies that are already disclosed upstream and have
  no exploitable surface in this codebase — please report those upstream.
- Best-practice deviations without a demonstrable exploit (e.g. "you should add
  HTTP header X"). Open a regular GitHub issue instead.

## Trust model

This section is the single source of truth for the project's trust
boundaries. Every code reviewer, contributor, auditor, and operator
reads this before proposing or accepting a security change. Code
grants and proxy gates derive their behaviour from the matrix below
— if a row here disagrees with what the code does, that is a bug to
file, not a deviation to debate.

### Roles

| Role | Identity source | Bypasses RLS? | Typical caller |
|------|-----------------|---------------|----------------|
| `anon` | no JWT, anon API key | no | unauthenticated browser |
| `authenticated` | valid JWT, `role=authenticated` | no | logged-in browser/mobile |
| `service_role` | `SERVICE_ROLE_KEY` as bearer or `apikey` header (constant-time match); a `role=service_role` JWT claim is demoted to `authenticated` (`proxy-go/middleware/rls.go:claimsFromJWT`) | **yes** | server-side process only |
| `admin` (DBA) | direct PG connection as `postgres` | yes | migrations, ops, never network-reachable |

`anon` and `authenticated` are the only roles intended to be reachable
from a network client. `service_role` MUST NOT appear in any browser
bundle and SHOULD NOT be the default credential of any client SDK
constructor. `admin` is out of band — direct PG access only.

### Capability × role matrix

`ALLOW` = explicitly permitted. `DENY` = refused at the gate.
`COND` = conditional, see enforcement column. A `COND` cell that
turns out to mean "everyone always" is a bug. A row missing from
this matrix is a bug.

| Capability | anon | authenticated | service_role | Enforcement |
|------------|------|---------------|--------------|-------------|
| REST: GET `/rest/v1/{table}` | COND | COND | ALLOW | per-table GRANT + RLS policy; default-deny for `anon`/`authenticated` (`docker/init.sql` "no blanket grants" block) |
| REST: write `/rest/v1/{table}` | COND | COND | ALLOW | per-table GRANT + RLS policy |
| REST: `/rest/v1/rpc/{fn}` | COND | COND | ALLOW | explicit `GRANT EXECUTE` per function; `PUBLIC EXECUTE` revoked (`migrations/20260519120000_revoke_public_function_execute.sql`, round 28) |
| WebSocket: open `/ws/{queryId}` | COND | ALLOW | ALLOW | `REQUIRE_AUTHENTICATED_WS=true` refuses anon; audience binding scopes deltas, enforced from the transactional `pgr.subscription_meta` catalog not shmem (inv. 15) (`proxy-go/realtime/`) |
| HTTP presence `/ws/_presence/{ch}` | COND | ALLOW | ALLOW | same audience gate; outside per-IP WS cap (round 22) |
| Storage: download from public bucket | ALLOW | ALLOW | ALLOW | bucket `public=true` |
| Storage: download from private bucket | DENY | COND | ALLOW | owner-match (`proxy-go/routes/storage.go`) |
| Storage: upload | DENY | ALLOW | ALLOW | any anon upload refused (round 13); per-key advisory lock serialises writers (round 17) |
| Storage: overwrite existing object | DENY | COND | ALLOW | same-owner check + atomic upsert (round 14) |
| Auth: signup / token / refresh | ALLOW | ALLOW | ALLOW | rate-limited per real-IP (`middleware/rate_limit.go`) |
| Auth: password reset / magiclink / verify | ALLOW | ALLOW | ALLOW | atomic token consume (F6 round 13); SMTP required in production (F5 round 26) |
| Auth: anonymous signin `/auth/v1/anonymous` | COND | COND | COND | **default-deny** — `ALLOW_ANONYMOUS_SIGNIN=false` returns 503 (round 34); when enabled mints a short-lived role=anon JWT (`ANONYMOUS_JWT_TTL`, default 3600s), no DB row, no refresh, rate-limited per-IP by a separate `ANONYMOUS_RATE_LIMIT` bucket (default 10 × `AUTH_RATE_LIMIT` = 300 per `ANONYMOUS_RATE_WINDOW`, default 60s) |
| Auth: admin user CRUD | DENY | DENY | ALLOW | `requireServiceRole` empty-key guard (`auth/jwt.go` round 24) |
| Auth: full JWT validation | COND | COND | COND | empty `JWT_SECRET` fails closed in `GenerateToken`/`ValidateToken`/`requireJWT` (round 26 F1 CRITICAL) |
| Edge function: call any function | COND | ALLOW | ALLOW | invokes function with caller's RLS context |
| Edge function: HTTP runtime upstream | n/a | n/a | n/a | `validateUpstreamURL` rejects IP literals, dotted FQDNs, loopback bare names (round 28 F3) |
| `/api/sql` raw SQL endpoint | DENY | DENY | COND | `ENABLE_SQL_ENDPOINT=true` AND service_role bearer; refused outright in `PGSTACK_ENV=production` validator |
| Webhook CRUD | DENY | DENY | ALLOW | secret stored AES-256-GCM-encrypted at rest |
| `pgr.subscribe` (registration) | DENY | DENY | ALLOW | revoked from PUBLIC; app callers go through `SECURITY DEFINER` wrappers with fixed SQL (see `docs/specs/pg_reactive_spec.md` §9.4) |
| OTP `request_otp` / `verify_otp` | DENY | DENY | ALLOW | service-role-only — raw token returns from PG; round 30 grants explicit |

### Cross-cutting invariants

These are properties the whole stack maintains. They override any
per-capability rule that contradicts them.

1. **No blanket `GRANT ALL ... TO authenticated`** on the public schema. New tables are default-deny for `authenticated`/`anon`. The bootstrap revokes the PostgreSQL default; `migrations/20260515200000_revoke_blanket_grants.sql` enforces it on existing deployments (round 12 F3).
2. **No `PUBLIC EXECUTE` on `public.*` functions.** Functions are default-deny; expose to RPC by explicit `GRANT EXECUTE TO {role}`. Owner-loop applies the rule across `postgres` + `current_user` so multi-tenant function owners are covered (round 28 F1 + round 29 F1). **PostgreSQL quirk**: `ALTER DEFAULT PRIVILEGES ... REVOKE EXECUTE ... FROM PUBLIC` does NOT actually defeat the built-in `PUBLIC=EXECUTE` default for new functions (works fine for tables). The actual enforcement is a `ddl_command_end` event trigger `pgstack_revoke_public_execute` (defined in `docker/init.sql`) that runs `REVOKE EXECUTE ON FUNCTION ... FROM PUBLIC` after every `CREATE FUNCTION`/`CREATE PROCEDURE` in `public`. Round 33 / audit F1 (the F1 label is shared with the separate round-33 sub-claim pass in invariant 11).
3. **`SECURITY DEFINER` requires pinned `search_path = pg_catalog, pg_temp`** plus fully-qualified object refs. Any docs/examples that violate this are bugs.
4. **`X-Forwarded-For` / `X-Forwarded-Proto` are only honoured from `TRUSTED_PROXIES`.** Without that env, the proxy uses kernel-attested `RemoteAddr` and ignores all forwarded headers. The XFF chain is walked right-to-left, skipping trusted-proxy hops, so the nginx `$proxy_add_x_forwarded_for` append pattern cannot be spoofed (round 22 F1). `X-Real-IP` is never honoured (round 23 F1).
5. **`chiMiddleware.RealIP` is NEVER added to the router.** It rewrites `RemoteAddr` from spoofable headers and defeats every gate downstream. `proxy-go/middleware/composition_test.go` "negative pin" test guards this (round 25 HIGH).
6. **Empty `JWT_SECRET` ⇒ all auth refused, not bypassed.** `GenerateToken`/`ValidateToken`/`requireJWT` are fail-closed (round 26 F1 CRITICAL).
7. **Empty `SERVICE_ROLE_KEY` ⇒ no admin requests succeed.** Round 24 empty-key guard.
8. **Raw OTP tokens never leave Postgres on any code path reachable from a non-`service_role` caller.** Round 30 HIGH.
9. **Edge function HTTP upstreams reject loopback bare hostnames** (`localhost`, `ip6-localhost`, …) in addition to IP literals (round 28 F3).
10. **HSTS `preload` is opt-in via `HSTS_PRELOAD=true`.** The `preload` directive is irreversible; never default-on (round 21 F5).
11. **JWT MUST carry a non-empty `sub` claim** to authenticate as anything other than anon — both the `/auth/v1/*` path (`auth/jwt.go:ValidateToken`) and the REST / RPC / storage path (`middleware/rls.go:validateJWT`) enforce this. Without the gate a signed-but-identityless token resolves as `authenticated` with `sub=""`, and RLS policies keyed on `auth.uid()` see NULL — any policy whose USING expression evaluates that to truthy becomes a row-level bypass (round 33 / audit F1).
12. **PG SQLSTATE class 22 (data exception) and class 23 (integrity constraint) map to 4xx, never 500** — 400 for everything except unique-violation `23505`, which maps to 409 Conflict (the main-package `error.go` mapping additionally returns 409 for foreign-key `23503`). `proxy-go/rest/rest.go:pgHTTPStatus` enforces this. An injection probe like `?id=eq.1' OR '1'='1` lands as an `invalid_text_representation (22P02)` for the integer cast — that is the client sending garbage, not the server crashing. Mapping 22xxx/23xxx to 500 made the `rest__sql_injection` regression test (Round 31 T3.5) flag every parameterized-but-malformed value as a possible crash. Round 33 / audit F2.
13. **No public app frontend bundle references `service_role` or the `/api/sql` endpoint.** Both are server-only; a browser bundle that ships either hands every visitor an RLS-bypass primitive. The in-browser "Setup Database" wizard (raw SQL posted to `/api/sql` under a service_role bearer) was removed from the vanilla shop variant in an earlier pass but lingered, dead-but-present, in the `angular` variant — found in the round-35 review. Round 36 widened the rule after the interactive tutorial (`examples/12-tutorial`) evaded it three ways at once: it lived under `examples/` (out of scope), used the camelCase `serviceRoleKey` identifier (pattern was `SERVICE_ROLE` only), and built the endpoint URL by concatenation (`apiBase + '/sql'`, never the literal `/api/sql`). Lint `SEC-R13` now walks both `apps/**` and `examples/**` `*.{html,js,mjs,ts}` and fails on any case-insensitive `service[_-]?role` token or raw-SQL endpoint reference, literal or concatenated; comment lines are skipped. Studio (`studio/`, the admin SQL console) is intentionally out of scope — it is not a public bundle.
14. **Every `SECURITY DEFINER` function in the extension install path is `REVOKE`d from `PUBLIC`.** PostgreSQL grants `PUBLIC EXECUTE` on new functions by default, so a SECURITY DEFINER function left un-revoked runs as the extension owner for *any* caller. The 0.1.4 fresh-install script created `pgr._persist_subscription` / `pgr._forget_subscription` (both SD) but omitted their `REVOKE` — the upgrade script had it — letting any role write the durable `pgr.persisted_subscriptions` catalog, which `pgr.restore_subscriptions()` then replays as the owner after a restart (persistence poisoning; Codex round-36 P0). Fix added the two `REVOKE`s plus `pgr.trigger_func()` (a trigger fires without requiring caller `EXECUTE`, so revoking it is safe). Lint `SEC-R14` reads `default_version` from `pg_reactive.control` and fails if any `CREATE FUNCTION ... SECURITY DEFINER` in that version's full-install or landing upgrade script lacks a matching `REVOKE EXECUTE ... FROM PUBLIC`. Note also that `pgr.subscribe`/`unsubscribe` are SECURITY INVOKER and call the revoked `_subscribe_internal` in the caller's context — granting the wrapper alone is **not** sufficient and is intentionally so: subscription registration for app roles goes through purpose-built SD wrappers only (docs/specs §9.4), never a raw grant.
15. **The WebSocket audience/mode gate reads the transactional catalog, never shmem.** `pgr.get_subscriptions()` reads the non-transactional shared-memory hash, which `pgr.subscribe()` mutates *out-of-transaction* — immediately visible to every backend. A re-subscribe that flips an audience-bound subscription to public *inside an uncommitted transaction* would therefore let a concurrent `/ws/{queryId}` connect read see it as public for the whole transaction window — an audience bypass that even outlives a later `ROLLBACK` as far as the racing reader is concerned. The gate (`proxy-go/realtime/ws.go:subscriptionMeta`) reads `pgr.subscription_meta(query_id)`, a `SECURITY DEFINER` lookup over the MVCC `pgr.persisted_subscriptions` catalog, so only committed audiences are ever enforced. Isolation spec `ext/specs/audience_visibility.spec` pins it: `proxy_gate` stays at the committed audience while a concurrent re-subscribe is in flight and after it rolls back, with the leaking `shmem_view` shown alongside to document why shmem must not be the source. Lint `SEC-R37` fails on any `proxy-go` line that pulls `audience` from `pgr.get_subscriptions()`. Round 37 F1 HIGH.
16. **Every WebSocket message is delivered only to connections bound to the message's GENERATION — the audience is bound once, at connect, and never re-evaluated against mutable state.** The connect-time gate (invariant 15) is necessary but not sufficient: a subscription re-registered under a different audience/mode must not keep streaming to a socket authorized under the old one (`public → private`, `tenant A → tenant B`). Batch-1 re-resolved the audience per delta inside the fan-out; the batch-2 audit (finding F-ORDER) showed that cannot work, because a delta's *epoch* is fixed by shared memory — `pgr.subscribe` mutates the shmem query/generation **non-transactionally** (visible the instant the LWLock releases, before the subscribe transaction commits), while any commit-time revocation signal races a concurrent DML that recomputes from that already-mutated shmem and commits first. The shipped mechanism (ext 0.1.6) makes generation the unit of delivery: every `pgr.subscribe`/`unsubscribe` draws a monotonic generation from `pgr.subscription_generation_seq`, stores it in BOTH the catalog (`pgr.persisted_subscriptions.generation`) and the shmem entry (via `pgr._subscribe_internal`), and the extension stamps the shmem generation into **every** NOTIFY it emits — `delta`, `overflow`, AND `invalidated` all carry `"gen":N` (`recompute.c`). The proxy binds each connection to the **committed catalog** generation it authorized against (`subscription_meta` → `Hub.Subscribe(queryID, cap, gen)`) and delivers a message only to connections whose generation **exactly equals** the message's `gen` (`Hub.BroadcastGen`). So a delta computed from a re-registered (new-epoch) query carries the new generation and is dropped for every old-epoch connection — regardless of commit ordering, and regardless of whether the re-subscribe ever commits (an aborted/in-flight re-subscribe leaves shmem at the new gen, deltas tagged new gen, old connections fail closed). A `resubscribed` notice (`{"type":"resubscribed","query_id":...,"gen":N}`) additionally drives `Hub.RevokeStale(queryID, N)` to disconnect every socket **not of generation N** so clients reconnect and rebind — that is **liveness**, not the data boundary. The comparison is `!= N`, not `< N`: generation is an **opaque epoch token**, not a commit-ordered counter, because `nextval()` is drawn before the catalog write, so a lower generation can commit *after* a higher one; an ordering test would leave the higher-generation socket alive after a lower generation became current (round 39 batch-2 gen-ordering audit, HIGH). `tests/e2e_ws_forder_test.mjs` proves the pre-commit-window leak is closed, `tests/e2e_ws_reauth_test.mjs` proves both audience-change directions, `ext/sql/14_generation.sql` pins the monotonic generation, and `proxy-go/realtime/ws_reauth_test.go` unit-tests that a gen-N+1 delta is dropped for a gen-N connection. Round 39 batch-2 F1/F-ORDER HIGH (supersedes the batch-1 per-delta re-check).
17. **Presence/broadcast are generation-gated, the initial snapshot is read atomically with its generation, and the proxy's ad-hoc channel namespace is reserved.** Corollaries of invariant 16. (a, F2 HIGH) presence join/leave/update and client `broadcast` are proxy-originated (not PG NOTIFY) and also go through `Hub.BroadcastGen(channel, payload, gen)` — delivered only to the sender's exact generation, so a stale socket never receives a current peer's event. Before the fix these used a generation-blind `Hub.Broadcast` and bypassed reauthorization entirely (an anon socket on a since-privated query still received a peer broadcast). (b, F3 + snapshot-TOCTOU MED/HIGH) the initial snapshot and the generation it belongs to are read consistently: `snapshotForGeneration` runs under **REPEATABLE READ** (so the generation check and the row read see one MVCC snapshot — a plain READ COMMITTED transaction takes a fresh snapshot per statement and a re-subscribe committing between them would pass the gen check on the old epoch while reading rows from the new one) and takes **ACCESS SHARE** on `pgr._snap_<id>` up front (so the re-subscribe, which rebuilds that table under ACCESS EXCLUSIVE in the same transaction that bumps the generation, cannot swap the rows out between the two reads). If a re-registration landed during connect — including the register-after-`RevokeStale`-sweep race — the generation no longer matches and the connection closes instead of shipping rows from a generation it never authorized; notify-mode uses `generationMatches`, and the snapshot send re-checks `sub.revoked()` first so a connection revoked mid-fetch ships nothing. (c, F-ADHOC) `pgr.subscribe` rejects the `_channel_`/`_presence_` prefixes (reserved for the proxy's catalog-less ad-hoc collaboration channels) so a real audience-bound subscription cannot land in the namespace where the connect-time generation re-check is skipped. (d, F-LIVENESS) `safeSend` sets a write deadline so a revoked socket wedged on a slow write still disconnects. (f, gen-ordering audit HIGH) presence is not only delivered generation-gated but **stored and read** generation-tagged: each presence row carries the writer's generation, and `Hub.PresenceList(channel, gen)` returns only rows of the caller's generation. The HTTP `PresenceHandler` passes the channel's current committed generation (from `subscription_meta`), so a reader authorized for one epoch never reads presence written under another — closing the leak where a stale-generation socket (which the `!= N` revoke now also disconnects, but which the ordering race could leave alive) wrote presence that the unfiltered map returned to everyone. `proxy-go/realtime/presence_test.go` (`TestPresenceList_FiltersByGeneration`) and `ws_reauth_test.go` (`TestRevokeStale_RevokesAnyNonMatchingGeneration`) pin it. (e, F-SNAP) `pgr.subscribe` DROPs and rebuilds `pgr._snap_<id>` on every (re-)subscribe (`pg_reactive.c`), because `CREATE ... IF NOT EXISTS` left a repointed `query_id`'s snapshot holding the PREVIOUS query's rows — which a fresh connection then read via the initial snapshot with a *matching* generation (the re-subscribe bumped both), so the generation gate could not catch it: a tenant-B client received tenant-A's rows. `tests/e2e_ws_snapshot_reauth_test.mjs` proves the snapshot no longer leaks across a query-changing re-subscribe, and `ext/sql/11_snapshot_drift.sql` pins both the rebuild and the residual drift-detection safety net. `proxy-go/realtime/ws_reauth_test.go` and `ws_scope_test.go` pin (a); the generation match in `BroadcastGen` is the data boundary for all of it. Lint `SEC-R39` fails on any reintroduced generation-blind `Hub.Broadcast`. Round 39 batch-2 F2/F3/F-ADHOC/F-LIVENESS/F-SNAP + gen-ordering/presence-state audit.
18. **`pgr.restore_subscriptions()` replays each persisted subscription as its `owner_role`, never as the superuser it runs as.** restore runs at every postmaster restart, invoked by the boot entrypoint as the superuser, and for each row re-executes the stored query — `pgr._subscribe_internal → pgr_snapshot_create` runs `CREATE UNLOGGED TABLE pgr._snap_<id> AS <query_text>`, i.e. arbitrary SQL, under the registrant's **saved search_path**. A subscription registered with an attacker-controlled search_path (pointing at the attacker's schema) and a query referencing an unqualified function/view therefore resolves that reference to the attacker's object and would run it **as the superuser** on the next restart (privilege escalation / RCE; gemini audit P1 CRITICAL). The function is **SECURITY INVOKER** (not DEFINER — PostgreSQL forbids `SET ROLE` inside a SECURITY DEFINER function, and DEFINER also carried its own latent escalation: a granted role could have run the whole replay as the definer-superuser) and, per row, does `RESET ROLE` then `SET LOCAL ROLE` to the subscription's `owner_role` before replaying — so the stored query can do no more than the owner could when it first subscribed. A row with no recorded `owner_role` fails closed (refused, not replayed as the superuser). **The `owner_role` must be the registrant, captured in the SECURITY INVOKER `pgr.subscribe` wrapper** (`current_user` there is the caller): `pgr._persist_subscription` originally evaluated `current_user` inside its own SECURITY DEFINER body, which is the **definer-superuser**, so `owner_role` was recorded as `postgres` for every subscription and the `SET ROLE` dropped to the superuser — i.e. did not drop. 0.1.8 passes the caller's role from `subscribe` into `_persist_subscription` so the drop is real. `ext/sql/15_restore_privilege.sql` drives the **real** subscribe path (a low-privilege role calls `pgr.subscribe`) and proves both that `owner_role` is the registrant and that the rebuilt snapshot is owned by it, not the bootstrap superuser; lint `SEC-R41` fails if `restore_subscriptions` is ever redefined `SECURITY DEFINER`. Round: gemini audit P1 (ext 0.1.7 made restore INVOKER + `SET ROLE`; 0.1.8 fixed the owner capture).
19. **Secure-by-default operational posture: `PGSTACK_ENV` defaults to `production`, and proxy health probes are deadline-bounded.** (a, gemini audit P3) an operator who forgets to set `PGSTACK_ENV` gets the strict validator — dev-only secrets, `ENABLE_SQL_ENDPOINT=true`, permissive CORS, and `REQUIRE_AUTHENTICATED_WS=false` all become fatal boot errors — rather than silently running the insecure dev posture in production. Dev/CI opt into the relaxed posture explicitly with `PGSTACK_ENV=development`, which the dev compose files set; the production compose files already pin `production`. (b, gemini audit P2) the Deno edge-runtime health probe (`functions.DenoHealth`) runs with a request-context deadline and a non-default `http.Client`, so a hung edge-runtime returns 502 promptly instead of wedging the handler goroutine and leaking a connection — a slow-loris DoS. The function-invoke reverse proxy is deliberately left streaming (tied to the client request context) so long-running edge functions are not cut off. `proxy-go/functions/deno_health_test.go` pins the timeout. The probe is also **mounted** at `GET /functions/v1/_health` as a literal route ahead of the `/functions/v1/{name}` wildcard — otherwise it fell through to `InvokeGet` as a function literally named `_health` and the bounded handler was never reached.
20. **`REQUIRE_EMAIL_VERIFICATION` is actually enforced: a new user is unverified until confirmed, and an email change re-arms verification.** The `pgstack.users.email_confirmed_at` column previously **defaulted to `now()`**, so every signup was auto-confirmed and the login gate (`RequireEmailVerification && email_confirmed_at IS NULL`) could never fire — email verification was a no-op (gemini audit P1). The default is removed (a new user is NULL/unverified); signup sets `now()` **only** when verification is off; admin/OAuth paths set it explicitly. An email change, when verification is on, **clears** `email_confirmed_at` (so the new address cannot inherit the old one's confirmed status) and issues a fresh verification token. `tests/e2e_auth_email_verify_test.mjs` proves an unverified user gets 403 at `/token`, succeeds after `/verify`, and is forced back to 403 by an email change. The schema default lives in `docker/init.sql` core and is synced to `cli/templates/bootstrap-core.sql`. **A verification token is bound to the email it confirms** (`pgstack.email_tokens.email`), not just the user — `/verify` sets `email_confirmed_at` only while the token's email still equals the user's current email, and an email change revokes outstanding verification tokens in the same transaction. Without this, a token minted for address X silently confirmed a later address Y (gemini audit finding 2). `tests/e2e_auth_stale_verify_token_test.mjs` proves a token issued for A cannot confirm a changed-to address C; migration `20260613130000` adds the column to existing databases.
21. **A password reset or change revokes every existing refresh token.** A reset is the response to a credential compromise; a stolen refresh token (default 30-day lifetime) that survives it can keep minting access tokens indefinitely. `auth.RecoverConfirm` (`/auth/v1/recover/confirm`) deletes all of the user's refresh tokens in the same transaction as the password update, and the authenticated change path (`auth.UpdateUser`, `PATCH /auth/v1/user`) does the same after changing the password (gemini audit P1). **Both happen in ONE transaction** — `UpdateUser` was rewritten to run every mutation (email, password, token revoke, metadata) inside a single `tx`, so a fault between the password update and the token delete can no longer leave the new password active while old refresh tokens still mint access tokens (gemini audit finding 4). `tests/e2e_auth_session_revoke_test.mjs` proves a pre-reset refresh token returns 401 after both flows.
22. **The proxy connects to PostgreSQL as the powerless `authenticator` role, never the superuser.** Connecting the proxy as the bootstrap superuser (`DATABASE_URL=postgres://postgres:…`) means a single missed `SET ROLE` — or any compromise that reaches the connection pool (SQLi, RCE, a leaked DSN) — runs with superuser power: bypass every RLS policy by default, `COPY … TO/FROM PROGRAM` (arbitrary OS command execution), `DROP DATABASE`, read `pg_authid` (every password hash). Discipline (always `SET ROLE`) cannot close this — the guarantee must be structural. `authenticator` is `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT`, a member of `anon`/`authenticated` (the admin plane uses a SEPARATE login role, `authenticator_admin` — **see invariant 24**; `authenticator` is deliberately NOT a member of `service_role`) but — because of `NOINHERIT` — holding **no privileges until it `SET ROLE`s**. The proxy runs two pools (invariant 24 covers the data/admin login-role split): the **data plane** (`SET LOCAL ROLE anon|authenticated` per request → RLS enforced) and the **admin pool** (its `authenticator_admin` connection assumes `service_role`, for trusted backend ops — auth, catalog, the SQL endpoint, the realtime gate, webhooks, storage, demo; service_role-key REST/RPC is routed here too). `service_role` is `BYPASSRLS` **but still NOSUPERUSER** — the worst case (full admin-pool compromise) can bypass RLS and DML app data, but still cannot exec OS programs, drop the database, or steal credentials. `authenticator`'s LOGIN password is supplied at deploy time via `AUTHENTICATOR_PASSWORD` (compose: `docker/20-authenticator-login.sh`; all-in-one: the entrypoint generates one when unset) — the shipped `docker/init.sql` creates the role `NOLOGIN` and ships no login-able role with a baked-in secret, so a deployment that forgets the password gets a `NOLOGIN` role and a proxy that fails closed, never a known-credential foothold. The only sanctioned superuser DSN is the all-in-one's fallback when the `authenticator` role is absent (standalone `pg_reactive` without the pgStack CORE — no RLS model to guard), marked `lint:allow=SEC-R42`. `tests/security/proxy__connects_as_non_superuser.test.mjs` connects AS the proxy's login role and proves it is NOSUPERUSER/NOBYPASSRLS/NOINHERIT, that `COPY … TO PROGRAM` / `pg_authid` / un-`SET ROLE`d app tables are all denied, and that the data role canNOT reach `service_role` (directly or via `RESET ROLE`) while the separate `authenticator_admin` role can (invariant 24); lint `SEC-R42` fails on any production proxy `DATABASE_URL` that connects as the superuser. gemini audit P2.
23. **Untrusted PR code never runs on the self-hosted runner that also runs deploy/release.** `.github/workflows/ci.yml` triggers on `pull_request`, so a malicious PR (especially from a fork) running on the self-hosted runner could persist on the box and steal publish/VPS credentials from a later trusted `deploy`/`release` run on the same machine — even though GitHub withholds secrets from fork-PR runs, the *runner* is the shared asset (runner-pinning). Every CI job selects its runner by event: `runs-on: ${{ (github.event_name == 'pull_request') && fromJSON('["ubuntu-latest"]') || fromJSON('["self-hosted", "Linux", "X64"]') }}` — PRs get an ephemeral GitHub-hosted VM (destroyed after the job), `push`/`workflow_dispatch` (trusted) get the self-hosted runner. `deploy.yml`/`release.yml` never trigger on PRs and stay self-hosted. The third-party `appleboy/ssh-action` in `deploy.yml` is pinned to an immutable commit SHA (not a mutable `@v1` tag) so a tag-move cannot inject code into the credentialed deploy. `deploy.yml` also triggers on `workflow_run` (CI completed) and deploys the exact CI-verified `head_sha`, gated on `conclusion == 'success' && event == 'push' && head_branch == 'master'` — so unverified or moving-master code is never shipped. The `workflow_dispatch` manual fallback is itself pinned to `github.ref == 'refs/heads/master'` — without that, a maintainer could dispatch `deploy.yml` against a feature branch and ship unverified code straight past branch protection + CI, since a dispatch's `DEPLOY_SHA` is `github.sha`, the selected ref's tip (gemini finding 3). Pinning to master alone still allows hand-deploying a RED master commit, so a dispatch additionally runs a first step (gated on `event_name == 'workflow_dispatch'`) that queries `ci.yml` runs for a SUCCESS on `github.sha` (push, master) and exits non-zero if none — holding the manual path to the same CI-green bar as the automatic `workflow_run` path (gemini finding 1, R23). gemini audit finding 3 (+ 7, action pinning + CI-gated deploy). `release.yml` (publishes Docker images + npm packages on a `v*` tag) is gated the same way: a `ci-gate` job requires a *successful* CI run for the tagged commit SHA before any publish job runs, and every third-party action it uses — including the credentialed `softprops/action-gh-release` and the `docker/*` push actions — is pinned to a full commit SHA, not a mutable `@vN` tag (gemini audit R4-4).
24. **The proxy connects with TWO login roles, so the data plane cannot escalate to the admin plane.** `authenticator` (data pool) is a member of `anon` + `authenticated` ONLY; `authenticator_admin` (admin pool) is a member of `service_role`. Because `authenticator` is NOT a member of `service_role`, a SQL injection on the data plane cannot reach `service_role`/BYPASSRLS even by `RESET ROLE` back to the session role and re-`SET ROLE` — the session role simply isn't a member (gemini audit finding 6, hardening beyond invariant 22's single-role model and beyond PostgREST's single-`authenticator` design). The proxy routes service_role-key REST/RPC/batch/edge-function requests to the admin pool (`RestDeps.poolFor` / `FunctionsDeps.poolFor`), since the data pool's role cannot assume `service_role`. The admin pool's DSN is `ADMIN_DATABASE_URL` (the `authenticator_admin` credential); when unset the admin pool falls back to `DATABASE_URL` (legacy single-role, where `authenticator` is a member of `service_role`). `authenticator_admin` is still NOSUPERUSER — the admin plane bypasses RLS but is not the OS-level superuser (invariant 22 still holds for it). `tests/security/proxy__connects_as_non_superuser.test.mjs` proves `authenticator` is DENIED `SET ROLE service_role` (directly and via `RESET ROLE`) while `authenticator_admin` is allowed; migration `20260613140000` adds the admin role to existing databases (with the documented operational cutover so the admin pool is repointed before the data role's `service_role` membership is revoked). **The split is enforced at startup, not just configured**: `verifyPoolRoles` (main.go) queries `pg_has_role(session_user,'service_role','MEMBER')` on the data pool (must be false), confirms the admin pool's connections actually assume `service_role`, AND checks the login role on BOTH pools is non-privileged AND over-constrained: every dangerous attribute false (`rolsuper`/`rolbypassrls`/`rolcreaterole`/`rolcreatedb`/`rolinherit`/`rolreplication`), a TRANSITIVE membership allowlist (data role → `anon`/`authenticated` only; admin role → `service_role` only, so service_role reached through an intermediate role is caught — and the login role must ALSO actually be a member of every allowlisted role that exists, since a missing required membership is a false-healthy startup that 500s authenticated requests at runtime, R11-2; and a completely ABSENT required role — anon/authenticated/service_role not bootstrapped — is fatal in production rather than a silent "verified", with PGSTACK_ENV=development as the explicit standalone-pg_reactive escape, R12-2), AND no direct ACL grants or object ownership (`pg_shdepend` deptype `o`/`a`), AND every allowlisted membership's per-edge options are safe — `pg_auth_members.admin_option`/`inherit_option`/`set_option` must be `f`/`f`/`t` (the allowlist bounds WHICH roles are reachable; the edge options bound HOW each grant behaves, and on PG16 they are per-membership, not derived from `rolinherit`), AND every reachable role is TERMINAL — anon/authenticated/service_role must be members of nothing, so a transitive edge between two allowlisted roles (e.g. `anon → authenticated WITH INHERIT TRUE`) cannot grant ambient privilege after a SET ROLE past the direct-edge check (R9-1); AND the TARGET roles the proxy SET ROLEs into are themselves validated (R10), not just the login role — anon/authenticated must be NOSUPERUSER NOBYPASSRLS NOLOGIN and own nothing (a table's owner bypasses its own RLS unless FORCE ROW LEVEL SECURITY), while service_role must be BYPASSRLS (the admin contract — a NOBYPASSRLS service_role is a false-healthy startup that silently RLS-filters trusted backend ops) and stays NOSUPERUSER NOLOGIN. The checks miss what the ownership, edge-option, terminal-role, and target-role checks catch (gemini audit R5-1 / R6-1 / R7-1 / R8-1 / R8-2 / R9-1 / R10-1 / R10-2 / R11-2 / R11-3 / R12-2): a SUPERUSER/BYPASSRLS DSN a `RESET ROLE` would escalate from; an `INHERIT` role that holds its members' privileges with NO `SET ROLE`; a `REPLICATION` role that can stream the database out; a role granted a dangerous predefined role — `pg_execute_server_program` (which yielded `COPY … TO PROGRAM`) or `pg_read_all_data` (RLS bypass); and a role with a **direct** `GRANT SELECT ON pgstack.users` or that **owns** an object — those privileges apply whenever the role is current, including after `RESET ROLE`, even under `NOINHERIT`; and an allowlisted membership whose grant carries `WITH INHERIT TRUE` (PG16 per-membership inherit overriding `rolinherit` → the role holds its member's privileges with NO `SET ROLE`, defeating the powerless-login model), `WITH ADMIN OPTION` (a login role without CREATEROLE can re-delegate the membership — on the admin plane, hand out `service_role`), or `WITH SET FALSE` (the proxy can never assume the role, breaking per-request RLS). All FATAL in production, warning in dev — `tests/security/proxy__startup_rejects_privileged_login.test.mjs` boots a production proxy against twenty-one variants (SUPERUSER, BYPASSRLS, INHERIT, REPLICATION+CREATEROLE+CREATEDB, `pg_execute_server_program`-member, transitive-service_role-via-intermediate, a direct ACL grant, object ownership, a privileged admin DSN, the three data-plane unsafe edges `WITH INHERIT TRUE`/`WITH ADMIN OPTION`/`WITH SET FALSE`, a `WITH ADMIN OPTION` grant of `service_role` on the admin plane, and a reachable non-terminal allowlisted role — `anon → authenticated WITH INHERIT TRUE` on the data plane and a `service_role` outgoing edge on the admin plane, plus three target-role profiles — `authenticated` BYPASSRLS, `service_role` SUPERUSER, and `authenticated` owning a table, a login role missing the required `authenticated` membership, a NOBYPASSRLS `service_role`, and a completely absent `authenticated`) and proves each exits fail-closed; so an incomplete cutover (REVOKE skipped) or a missing/wrong `ADMIN_DATABASE_URL` cannot silently boot an insecure or non-functional admin plane (gemini audit R4-1/R4-2); lint `SEC-R43` additionally fails on any in-repo bootstrap `GRANT … TO authenticator`/`authenticator_admin` carrying `WITH ADMIN OPTION`/`INHERIT TRUE`/`SET FALSE` — the self-inflicted form of R8 the runtime check would otherwise catch only at boot. `PGSTACK_ENV=production` additionally requires `ADMIN_DATABASE_URL` in `Config.Validate` (`config_test.go:TestValidate_ProductionRequiresAdminDatabaseURL`). A broken admin pool now degrades `/health` to 503 (`admin_connected:false`) instead of reporting 200, and the edge-function catalog reconnect loop waits 5s between attempts (`time.NewTimer`) instead of spinning ~100 warnings/sec.
25. **Release PROMOTES the exact image CI built and tested for the commit — it never rebuilds from a mutable base.** `release.yml` previously rebuilt both Docker images at tag time from `./Dockerfile.dev` (`FROM postgres:16-bookworm`, a mutable tag) and `./proxy-go/Dockerfile`, so the published artifact was assembled fresh — from whatever the base tag and apt repos served at that moment — and had never passed the suite as those exact bytes; a base republish (or upstream-tag compromise) between the green CI run and the release silently changed what users `docker pull` even though `ci-gate` reported CI "passed" (gemini finding 7). Now CI builds each image ONCE, on a green master push, in `build-publish-images` (gated on the full test suite + `if: github.event_name == 'push' && github.ref == 'refs/heads/master'`, so PRs never publish) pushes it under the immutable per-commit staging tag `sha-<sha>`, and **smoke-tests that exact digest** (`@<digest>` with `--pull=always`, never a tag a persistent runner might have stale) on BOTH published arches (`linux/amd64` + `linux/arm64` via the job's QEMU, so the arm64 variant of the manifest can't ship unverified — gemini R24-1) — postgres: boots + `CREATE EXTENSION pg_reactive` loads; proxy: reaches its production validator and is asserted to print the SPECIFIC `JWT_SECRET still contains 'dev-only'` rejection (not merely exit non-zero, which a missing binary / loader error / panic would too) — and creates the `sha-<sha>` tag release resolves ONLY after both smokes pass, so a CI re-run whose smoke fails can never leave `sha-<sha>` pointing at an un-smoked image (gemini findings 1/2). The exercised digest is the artifact promoted, not only a separate compose build of the same source. `release.yml`'s `docker-proxy`/`docker-postgres` jobs no longer build: each resolves `ghcr.io/<owner>/pgstack-<img>:sha-${{ github.sha }}` to its digest — via `imagetools inspect --format '{{json .Manifest}}' | jq -r .digest`, because the `{{ .Manifest.Digest }}` template prints the whole human-readable inspect on current Buildx, not the digest (gemini finding 1) — and `docker buildx imagetools create`s the version tags from `${REPO}@${DIGEST}`, a manifest copy, no Dockerfile, no second base pull. The promoted digest is thus the exact image CI built and artifact-smoke-tested; the full functional suite covers the same source via compose. A tag on a commit that never produced a staging image (one predating this pipeline) fails closed (`imagetools inspect` errors). `tests/ci_supply_chain_test.mjs` enforces it structurally: no release job may build an image (`docker/build-push-action` / `docker build`), each shipped image must be promoted from ITS OWN repo's computed digest (`${REPO}@${DIGEST}` — not a mutable `:sha`/`:latest` tag, not an unrelated repo, not a snippet in dead code), the CI candidate publisher must `push: true` immutable `sha-${{ github.sha }}` tags and be gated on the security/E2E suite, and a release that drops a promote fails — each locked in as a mandatory mutation self-test. The push-only `build-publish-images` is the one CI job permitted `packages: write` + an unconditional self-hosted runner, because its `if` evaluates false under a pull_request event (it never runs untrusted code); the guard verifies that exemption by EVALUATING the job `if` against a PR context, not by trusting the job name. Supersedes the deferred "pin the base by digest" half-measure (which would have frozen base security patches): the base is pulled fresh each CI build, so patches still flow, and only what CI tested is shipped. gemini finding 7 (architectural — build-once, promote-digest). **R23:** the release version is the git tag — `ci-gate` rejects a non-SemVer tag (full semver.org grammar — `MAJOR.MINOR.PATCH[-prerelease]`, no leading zeros, no empty / `01` / dotted-empty prerelease identifiers, no `+build`; R24-2) and requires `sdk` + `cli` `package.json` to MATCH it before any publish, so `npm publish` cannot ship a stale `0.1.1` under tag `v0.2.0` (gemini finding 3); the npm jobs publish a pre-release under dist-tag `next`, never `latest`, so `npm install` can't hand everyone an RC (gemini finding 2). The candidate guard additionally enforces tag-after-smoke ORDER (the `sha-<sha>` create must follow both smoke steps), strips comments + dead code before matching smoke/promote signatures (a signature in a `#` comment or a `while false` block no longer satisfies it), pins the candidate job's own `if` to push-on-`refs/heads/master`, and counts `REPO`/`DIGEST` as assigned exactly once including via `export`/`declare`/`printf -v` (gemini finding 4). **R27 (architectural — the auditor's own conclusion that regex-analysis of inline workflow shell had hit its limit):** the critical gate/validation/promote/smoke LOGIC now lives in `.github/scripts/*.sh` — `validate-release-version.sh` (strict SemVer + sdk/cli match), `require-green-ci.sh` (CI-green for the SHA, shared by release ci-gate + deploy manual gate), `npm-dist-tag.sh`, `compute-docker-tags.sh`, `promote-image.sh`, `smoke-postgres.sh`, `smoke-proxy.sh` — and is tested by EXECUTION in `tests/release_scripts_test.mjs` (run good/bad versions/tags/CI-counts through the scripts and assert exit code + output; jq/gh stubbed via `JQ_CLI`/`GH_CLI` seams). `tests/ci_supply_chain_test.mjs` is reduced to verifying the workflows CALL the right script (in LIVE code — a name in a `#` comment doesn't count) and don't SILENTLY DISABLE the step — `if: false` / `if: always()` (evaluated), `continue-on-error`, a fake `shell: bash -c '…' {0}` / `shell: true {0}` that never executes the script, or a `|| true` / `|| :` that swallows its failure — plus the structural invariants above (triggers, pinning, runner isolation, no-rebuild, candidate build/needs, checkout creds). All seven scripts are execution-tested (the Docker/GHCR ones — promote/smoke — via a stubbed `docker`, so replacing any with `exit 0` is caught, not merely file-existence), and `promote-image.sh` fails closed when the digest can't be resolved or the tag set is empty (R28). These exotic disables require EDITING the workflow, by an actor who could also edit the guard or the scripts — i.e. a malicious committer, addressed by branch protection plus the `.github/CODEOWNERS` rule on `.github/` (which declares the owners; it is enforced only when the `master` branch-protection rule has "Require review from Code Owners" enabled), not an ever-growing regex; the guard's job is catching ACCIDENTAL regressions, and the script execution tests make the critical logic's behavioral correctness a tested artifact rather than a grep. **R31 (the step-disable check was a blocklist):** it enumerated only `|| true` / `|| :` / `|| exit 0`, so a LIVE shell wrapper that still swallows the script's non-zero exit slipped through — `if ! bash …/script.sh …; then echo ok; fi`, `bash …/script.sh … || echo ok`, `bash …/script.sh … | cat` (stripDead can't remove these — the `if` is reachable). The five critical gating steps (deploy + release `require-green-ci`, release `validate-release-version`, both `promote-image`, both `smoke-*`) now ALSO pass through an ALLOWLIST (`bareCall`): after stripping comments + dead code, the step must be a BARE single-command invocation of the script — no conditional/loop wrapper, no control operator (`|| && | ; &`), no command substitution, no extra command line (only optional `set -…` lines) — so the script's non-zero exit ALWAYS fails the step. The shared blocklist also grew to catch `|| echo` / `|| printf` for the non-bare sites (npm publish, the `imagetools` sha-tag). Locked in as five mutation self-tests (96 total). **R32 (the guard FOUND the right element but didn't BIND it):** three "presence ≠ correctness" gaps closed. (a) The candidate `sha-${{ github.sha }}` tag is now required to be created from the SAME `@digest` each image's smoke verified — same image repo AND the same `steps.*.outputs.digest` ref — so a `pgstack-proxy:sha-…` tag sourced from the postgres digest, a foreign step's digest, or a mutable `:latest` is caught (the old check verified only the tag step's presence + tag-after-smoke order). (b) The promote check inspected the FIRST `promote-image.sh` step in the job; a decoy promote with the right `${{ github.sha }}` placed before a real promote on a foreign SHA passed — now EVERY step that promotes a given image (found by image, across all jobs) must pass the SHA/bare/enabled checks. (c) `npm publish --tag` presence ≠ the value being the script's result — the guard now captures the variable assigned from `$(… npm-dist-tag.sh …)` and requires `--tag "$VAR"`, so `NPM_TAG=$(…); npm publish --tag latest` (ignoring the pre-release routing) is caught. Three more mutation self-tests (101 total). **R33 (one level deeper than R32 — the digest itself wasn't bound to the build):** the candidate guard bound the smoke digest ↔ the sha-tag digest (both must use the same `steps.*.outputs.digest`), but accepted ANY step id — so renaming the real `docker/build-push-action` step's id (`proxy` → `proxy_build`) and adding a decoy step `id: proxy` that writes `digest=sha256:…` to `$GITHUB_OUTPUT` let smoke + sha-tag consume the decoy's attacker-chosen digest while staying internally consistent (and actionlint-clean). The guard now maps each image to the id of ITS build-push-action step (by Dockerfile), requires that build step to HAVE an id, and requires the smoke step AND the sha-tag line to reference `steps.<that-build-id>.outputs.digest` specifically — so the only digest that can flow to smoke/promote is the one the build actually produced. Three more mutation self-tests (104 total). **R34 (OVERWRITE after a correct step — last-writer-wins):** the guard validated the canonical step but didn't forbid a LATER step (or a second line) that re-points the same artifact. Three vectors closed: (a) a 2nd `imagetools create` — a later step or a 2nd line — re-creating `pgstack-<img>:sha-${{github.sha}}` from `:latest` or a foreign digest after the correct tag step → the candidate guard now requires EVERY `imagetools create … <img>:sha-…` line across ALL steps (not just the first) to source the build digest; (b) a direct `docker buildx imagetools create -t <release-tag> <img>:latest` after the correct `promote-image.sh` → no release job may run `imagetools create` directly (promotion is delegated to promote-image.sh, which sources the CI-built digest); (c) `npm dist-tag add <pkg> latest` after the correct `npm publish --tag "$NPM_TAG"` → no release job may run `npm dist-tag add … latest` (the dist-tag comes only from `--tag $NPM_TAG` at publish, preserving npm-dist-tag.sh's pre-release routing). Four more mutation self-tests (108 total). **R35 (R34's line/literal matching wasn't shell-equivalent):** the overwrite bans matched on a single physical line, so a shell line-continuation (`docker buildx imagetools \`⏎`create …`, `npm dist-tag \`⏎`add …`) split the command token across lines and slipped, and the `dist-tag add … latest` ban keyed on the literal word `latest` so `TAG=latest; npm dist-tag add … "$TAG"` slipped. Fix: `lr` now joins line-continuations first (`\`+newline+indent → a space) so a command is matched as the single logical command it runs as, and the release `dist-tag` ban forbids ANY `npm dist-tag add` (the dist-tag must come only from `--tag $NPM_TAG` at publish — a `$TAG`/`${…}` target can't be enumerated literally). The real workflows use `\`-continuations only in test jobs (not in the imagetools/dist-tag paths), so the join is a no-op there. Four more mutation self-tests (112 total). **R36 (still text-matching, not shell-matching — quoted-fragment bypass):** R35 joined line-continuations but the overwrite checks still searched for literal tokens, so the shell's quote-removal beat them — `docker buildx image"tools" create …`, `npm dist"-tag" add …`, `npm dist-tag a"dd" …` are all valid GitHub Actions YAML and the shell collapses each quoted fragment into one argv word (`imagetools`, `dist-tag`, `add`). Fix: the three overwrite checks now TOKENIZE to argv before matching — `shellCommands(lr(text))` splits into simple commands on unquoted `; | & ⏎ ( )` and each into argv with quote CHARACTERS removed, then they match argv SEQUENCES (`["imagetools","create"]`, `["npm","dist-tag","add"]`). This reproduces shell quote-removal (`image"tools"` → one token `imagetools`) AND keeps the command-vs-argument distinction (`echo "imagetools create"` stays a single argv token in position 1, so it is NOT matched as the command `imagetools` + `create` — no false positive). Four more mutation self-tests (116 total). **R37 (the argv tokenizer didn't model all of Bash's quote-removal):** it removed ordinary `'`/`"` but treated `$'…'` as `$` + a quoted string, so Bash ANSI-C quoting concatenated `image$'tools'` / `dist$'-tag'` / `a$'dd'` into one argv word (`imagetools` / `dist-tag` / `add`) that the checks missed (all actionlint-clean). Fix: `shellCommands` now models `$'…'` (ANSI-C, with backslash escapes) and `$"…"` (locale) as quote-removal-and-concatenate, AND ordinary unquoted backslash escaping (`a\dd` → `add`, which shellcheck flags but the guard now also catches). Five more mutation self-tests (121 total). **R38 (command-substitution token bypass):** a command or sub-verb token can itself be a command substitution whose OUTPUT the shell runs as that token — `docker buildx "$(printf imagetools)" create`, `npm "$(printf dist-tag)" add`, `npm dist-tag "$(printf add)"` (all actionlint-clean) — and the value is only known at runtime, so it can't be resolved statically. Fix is fail-closed: a token containing `$(…)` or a backtick (`isDyn`) in a command/sub-verb position matches the forbidden sequence as a WILDCARD, so the guard flags it rather than missing it; `shellCommands` also consumes `$(…)` and backticks as balanced units so an unquoted substitution doesn't split the command. The real workflows have no dynamic command tokens (the one `$()` is `NPM_TAG="$(bash …npm-dist-tag.sh…)"`, an assignment in its own simple command, never a 2-/3-token forbidden sequence), so this is purely fail-closed armor. Six more mutation self-tests (127 total). The residual is now genuinely real-shell-only (arbitrary parameter/alias expansion that resolves to a forbidden command), which the R27 architecture answers by pushing such logic into execution-tested `.github/scripts/*.sh` rather than dynamic command construction in the workflow.

## Ritual: every security finding leaves three things behind

After every audit round, CVE, or pentest finding, the fix PR MUST
also add:

1. **One negative regression test** in `tests/security/` (or the
   relevant `*_test.go` next to the code) that fails on the
   pre-fix code and passes after. No more "we caught it once and
   hope we never lose it".
2. **One updated row in the trust matrix above** (or one new row,
   or one new cross-cutting invariant). If the finding has no row
   to update, you are documenting a gap — that itself is the work.
3. **(when the class allows it) One new lint rule** in
   `tests/lint/`. If the mistake can be matched by grep or AST,
   codify it. Examples already there: `SECURITY DEFINER` without
   pinned `search_path`, `GRANT EXECUTE ... TO authenticated` next
   to a `RETURNS TEXT` raw-token function.

The pull request template (`.github/PULL_REQUEST_TEMPLATE.md`) has
the checklist. Reviewers refuse security-tagged PRs that skip it.

This ritual is what turns audit rounds from "find / fix / forget"
into cumulative hardening. Round N+1 should run against rails N
built.

### Required production configuration

The proxy will refuse to start in `PGSTACK_ENV=production` mode without:

- Real secrets: `JWT_SECRET` (min 32 chars, enforced), `ANON_KEY` and
  `SERVICE_ROLE_KEY` (non-empty and not publicly-known dev values; 32+ random
  bytes recommended), `SECRETS_ENCRYPTION_KEY` (base64 decoding to exactly
  32 bytes — an invalid key is a fatal startup error). Generate via
  `openssl rand -base64 32`. `POSTGRES_PASSWORD` is enforced by the compose
  file's `${POSTGRES_PASSWORD:?}` interpolation
  (`examples/docker-compose.prod.yml`), not by the proxy validator.
- `SECRETS_ENCRYPTION_KEY` — unconditionally required in production; it
  encrypts edge function environment variables and webhook signing secrets
  at rest (AES-256-GCM).
- `ENABLE_SQL_ENDPOINT=false` — setting it `true` is a fatal startup error in
  `PGSTACK_ENV=production` (no escape hatch). Outside production the
  `/api/sql` handler additionally always requires a `service_role` bearer.
- `REQUIRE_AUTHENTICATED_WS=true` — with `JWT_SECRET` and `ANON_KEY` set (both
  already required in production), leaving it `false` is fatal.
- `SMTP_HOST`, `SMTP_USER` and `SMTP_PASS` — without SMTP the dev mailer logs
  reset/magiclink/verification URLs to the console (round 26 F5).
- `ENABLE_DEMO_ENDPOINT=false` — `true` is fatal unless `PUBLIC_DEMO_SITE=true`.
- `ALLOW_PERMISSIVE_CORS=false` (default in production).
- `TRUSTED_PROXIES` configured if you sit behind a reverse proxy; otherwise
  `X-Forwarded-For` is ignored to prevent rate-limit bypass.
