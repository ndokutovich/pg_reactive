The Challenge

The Reactive Query Gap

Existing solutions each solve a piece of the puzzle, but none deliver the full picture.

CDC

CDC

Debezium, Supabase, ElectricSQL

Row-level events per single table. No JOINs, no aggregates, no WHERE filtering across tables. You get raw WAL changes, not query results.

Polling

Polling

Hasura, Manual Refresh

Re-execute the full query on a timer. High latency (seconds), wasted compute on unchanged data, no delta information -- just full snapshots.

IVM

Incremental View Maintenance

pg_ivm

Updates materialized views in-place on DML. Limited SQL support: no HAVING, no window functions, no CTEs, no LIMIT.

No existing tool delivers query-level deltas (exact inserted and deleted rows) for arbitrary SQL -- JOINs, GROUP BY, HAVING, window functions, CTEs.

8 Queries, Graduated Complexity

From simple filtered SELECTs to CTEs and window functions.

ID SQL Constructs Description
Q1 JOIN x2 + WHERE Orders with customer+product names, filtered by region
Q2 Single-table WHERE Products in 'electronics' category
Q3 JOIN x2 All order details with customer and product names
Q4 LEFT JOIN + GROUP BY + SUM Revenue per customer (including those with zero orders)
Q5 GROUP BY + HAVING Categories with average price above $30
Q6 Window function (RANK) Price ranking within each product category
Q7 CTE + JOIN Top customers by total order count
Q8 ORDER BY + LIMIT 50 most recent orders

Q4: LEFT JOIN + GROUP BY + SUM

SELECT c.name, COALESCE(SUM(o.total), 0) AS revenue FROM customers c LEFT JOIN orders o ON o.customer_id = c.id GROUP BY c.name

Q6: Window Function (RANK)

SELECT name, category, price, RANK() OVER ( PARTITION BY category ORDER BY price DESC ) AS price_rank FROM products

Scenario S2

Change Delivery Latency

Time from INSERT commit to client notification (100 iterations, p50)

Debezium: 4.3s median (92/100 timeouts via Kafka pipeline). Supabase: could not measure reliably.

pg_reactive adds ~5ms to compute EXCEPT-based deltas. In return, you get exact inserted/deleted rows for any SQL -- JOINs, GROUP BY, HAVING, window functions. Other push-based approaches deliver only single-table row events.

Scenario S1

Write Overhead

pgbench INSERT throughput (10s, 4 clients)

pg_reactive has the highest write overhead because it performs synchronous EXCEPT-based recompute inside each DML trigger. For write-heavy workloads, enable pg_reactive.async_recompute = on to move delta computation to a background worker.
Scenario S5

Subscription Count Scaling

Write TPS with increasing active subscriptions

Synchronous EXCEPT recompute executes once per subscription per DML statement, explaining the steep initial drop. pg_ivm's incremental approach scales more gently but supports fewer SQL constructs.

Conclusion

Key Takeaways

🔍

Only Full-SQL Reactive

pg_reactive supports JOINs, GROUP BY, HAVING, window functions, CTEs -- no other push-based approach does. 8/8 queries passed.

⏱

Sub-6ms Query Deltas

Exact inserted/deleted rows for any SQL query, delivered via pg_notify in under 6ms (p50). Trades write overhead for query-level precision.

🧩

Standard Extension

No PostgreSQL recompilation needed. Install with CREATE EXTENSION, configure with shared_preload_libraries. Uses the same public hook APIs as pgvector, PostGIS, pg_stat_statements.
